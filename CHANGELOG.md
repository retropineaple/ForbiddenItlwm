# Changelog

## Unreleased

- Adds `ITLAWDLAfCount`, `ITLAWDLAfGapBins` and `ITLAWDLAfGapMaxMs`, the gaps between action frames heard on the listener's channel, and `tools/diag/airdrop_paths.py`, which shows whether an AirDrop transfer runs on `awdl0`, `en1` or the wired `en0`.
- Continuity Camera: `-itlawdlpeeralive` and `-itlawdlndpkeep` (Sequoia 15.x, experimental) keep the iPhone in the family's peer table, which dropped it every 6 to 11 s and reset the real-time group. See BOOT-FLAGS.md. `tools/diag/awdl_ctl.py` is kept for reference (the ioctl is refused with errno 102).
- Continuity Camera: `-itlawdlsyncalign` (experimental) aligns the sync TLV and the AW events with the iPhone's AW clock and master, as a real Mac's firmware does (measured on a real Mac: UMI at the iPhone's AW 37020, slot 7, answered by its RTG TLV in 14-106 ms). See BOOT-FLAGS.md.
- Continuity Camera: `-itlawdlumitx` (experimental, with `-itlawdlawevents`) transmits the family's real-time UMI as a unicast master indication to the iPhone and reports its real transmit status, replacing the fabricated acknowledgement. See BOOT-FLAGS.md.
- Continuity Camera: `-itlawdlawevents` (experimental) posts the AWDL availability-window events 41/43 so the family can send its real-time UMI, the frame a real Mac sends to make the iPhone join the real-time group and adopt the Mac's channel plan. Records the UMI requests it then makes. See BOOT-FLAGS.md.
- Continuity Camera: `-itlawdlull` (Sequoia 15.x, experimental) enables the family's ultra-low-latency infrastructure mode so the iPhone stays on the infrastructure channel instead of hopping to 149 for half of every cycle (the cause of the 2 Hz judder measured on llw0). See BOOT-FLAGS.md.

- **Fix: AirDrop sends died with `unexpected-40` ("Message too long") whenever a wired interface was at the default MTU of 1500.** Read in the assembly: macOS gives `awdl0` 1500 only when the controller is `AppleBCMWLANCore` and 1484 for every other controller (`peerToPeerConfigureIfnet`, `mov esi, 0x5dc` or `0x5cc`), so on Apple's own hardware `awdl0` equals the wired MTU and this can't happen. The driver now sets 1500 itself after the family has run, as Apple's does, and registers 1500 instead of the old 1428 (Sequoia kext; `itlawdlmtu=N` chooses another value, 1484 is the family's). The data path already carried 1500 bytes: 2,048-byte pool buffers, 1,514-byte transmit ring entries, a codec that accepts 1,500 IPv6 bytes. No user setting is needed any more; lowering the wired MTU still works as before. On the failing run: five sends of 50 MB and 27 MB died, 474 "Message too long" lines, with `en0` and `en1` at 1500 and `awdl0` at 1484. Not yet measured on hardware.
- **Tools:** `tools/diag/airdrop_check.py` finds where an AirDrop attempt breaks: interface MTUs, neighbours and sync frames, a classifier over sharingd, wifip2pd and rapportd logs (missing endpoint, EMSGSIZE, broken connection, timeout, no llw0), the driver's counters, optional discovery (`--discover`), an MTU ping ladder (`--ping`) and counter deltas over a window in which you run a transfer (`--window`), and names the most likely cause. `tests/airdrop_check_test.py` checks it on the real output of that failure; `tests/awdl_mtu.cpp` checks the MTU choice.
- **Fix: the Sonoma kext didn't build** since the realtime access-category code, which calls a WCL-only function; it now falls back to best effort there.
- **Fix: the station's power state no longer flaps with every pause in the AWDL data.** The "AWDL data is moving" state came from a 2-second test, so it flipped (19 power tables in a few minutes) and each power-save transition sends a null frame on the station's channel, pulling the radio off the AWDL channel. The state now holds for 30 seconds after the last AWDL data. New keys: `ITLAWDLPmRecipeSent`, `PmRecipeFlags`, `PmRecipeErr`, `PmFlips`.
- **Tools:** `tools/diag/cc_analyze.py` judges a run from the registry (command ring, Block Ack, the station's power table, loss by sequence number, gap phase against the beacons and by beacon class, the iPhone's rates, what we advertise) with PASS/FAIL checks, live, on a saved dump, or as the difference between two dumps. `tests/cc_analyze_test.py` checks its maths and decoding against a recorded run (`tests/fixtures/cc-run-2026-11-18.txt`) and synthetic ones.
- **Reversed from Apple's driver: the Wi-Fi station should sleep more, not less, while AWDL runs.** `AppleBCMWLANPowerManager::configurePowerSaveForAWDL` extends the station's DTIM listen interval and enables early beacon termination, opportunistic power save and nap. This driver switched the station's power save off while AWDL data moved, and beacon abort was never enabled at all (the flag that sets it was never set). Now the station keeps power save on, enables beacon abort, and skips DTIM periods (`itlawdlcoexskipdtim=N`, default 2) while AWDL data moves. Not yet measured on hardware.
- **Found: the receive gaps are tied to the access point's beacons.** On the test Mac 63% of the camera stream's gaps end 12.8 to 38.4 ms after the last beacon from the Wi-Fi station's access point (chi-square 605), so the AX200 leaves the AWDL channel for the station about once per beacon interval and stays 13 to 38 ms. About 40% of the gaps are not tied to the beacons. New registry data: `ITLAWDLGapPhaseBins`, `GapPhaseMissing`, `GapPhaseByClass` (by DTIM beacon class), `BeaconsSeen`, `BeaconIntervalUS`, `BeaconDtimPeriod`. Cause of the long visit not yet known.
- **Ruled out: the listener on one RX chain.** The firmware image's own command-version table (`iwlwifi-cc-a0-68.ucode`, TLV 48) lists `PHY_CONTEXT_CMD` as version 3, which the driver promotes from 1, 1 to two chains, so the listener has been on two. The same table has no entry for `LOW_LATENCY_CMD` (MAC config group, command 3): the AX200 firmware does not implement it, which is why the command never completed. `ITLAWDLPhyCmdInfo` stays as a read-only record of what each PHY context gets.
- **Ruled out: the advertised width.** `-itlawdlcoexclass20` (rewrites the operating classes in the TLV 18 we send to the 20 MHz class while the listener is at 20 MHz; `include/AWDLChannelClass.hpp`, host-tested) rewrote nothing on the test Mac, because macOS already announces class 124 (20 MHz). The iPhone's TID 7 frames are all HE at 20 MHz. Found by reading `channelSequenceMinimumBW` and the TLV 18 parser in IO80211Family. New registry data: `ITLAWDLCap{Own,Peer,OwnSent}Tlv{7,17,18}`, `ITLAWDLRxRatesTid7`.
- **Fix: a host command the firmware never completes no longer wedges the command ring.** The AX200's ring has 32 slots; `LOW_LATENCY_CMD` (sent with `-itlawdlcoexlowlat`) is never completed by its firmware, its slot stayed pending, and once the ring wrapped onto it every later command returned `ENOSPC`: no peer station, no Block Ack, no TID 7. The command is no longer sent (the flag is ignored), slots silent for 3 s are reclaimed, and `ITLAWDLCmd*` registry counters show timeouts, refusals by reason and reclaims. The earlier note that the firmware "refused" the command was wrong: errno 35 is `EWOULDBLOCK`, a timeout.
- **Diagnostics:** the Real Time Group TLV (type 31) of the iPhone's and of macOS's own action frames is recorded (`ITLAWDLRtgPeerTlv`, `RtgOwnTlv`, counts of the "ultra low latency infra active" bit). Found by reading `parseAWDLRealTimeGroupTLV` in IO80211Family.
- **Continuity Camera TID-7 BA / ADD_STA ENOSPC.** `cc-vo`: `BaTids=1` while TID-7 miss 11%. `cc-tid7`: `BaPeerAdded=No`, `BaBusyEvents=1696` all ADD_STA ENOSPC, BusySkips 113k. AppleBCMWLAN BA is per `ampdu_tid`. Fix: highest-TID ADDBA; 10 ms AddPeer retry (not 100 ms BaHandle abort); Continuity BA-setup hold skips sync/data/pause so ADD_STA owns the cmd ring. Notes: [docs/RE-continuity-tid7-ba.md](docs/RE-continuity-tid7-ba.md).
- **Continuity Camera realtime → EDCA VO (Apple ASM, AX200).** `AppleBCMWLANCoreMac` `setRealTimeMode` sets `wme_ac_sta` for VO (disassembly at `wme_ac_sta` iovar); `setLLW_PARAMS` drives `WLC_SET_VAR llw`. Port: `setLLW_PARAMS` / active peer-traffic registration arm realtime; AWDL/llw data TX uses `EDCA_AC_VO` while realtime (was forced BE); Continuity lowlat refresh waits until `BaPeerAdded` so ADD_STA is not starved by ENOSPC. Notes: [docs/RE-continuity-realtime-vo.md](docs/RE-continuity-realtime-vo.md).
- **Continuity Camera FollowsInfra (Apple ULL social-channel adapt, AX200).** Reverse of Sequoia Boot KC `IO80211Family` shows `adaptCommonSocialChannelForUltraLowLatencyInfra` / `AwdlFollowsInfra` / `setIsRTGUltraLowLatencyInfraActive`. Auto-follow is gated: only when Continuity is warm and the iPhone's AWDL slots already name the Mac's infra channel (or `-itlawdlcoexfollowsinfra`). An earlier Mac-only move onto infra while the phone stayed on 149 caused `move-uncertain` and broke Photo Booth. Notes: [docs/RE-continuity-follows-infra.md](docs/RE-continuity-follows-infra.md).
- **Continuity Camera: the iPhone's video stream now reaches the Mac (`-itlawdlllw`).** Two things stood in the way, both found by reading what the iPhone actually sends. Its camera frames are plain RFC 1042 (`aa aa 03 00 00 00 86 dd`, then IPv6), not AWDL-header frames, and the parser read the ethertype as a length and rejected every one (`DataRxMalformed` 11,705 of 11,902, thought at first to be aggregation). Broadcom's host code sends those frames to `llw0` and only Apple-header frames to `awdl0`; the driver now does the same, and `llw0`'s own transmit frames go out plain too, where before they were wrapped in the AWDL header through `awdl0`'s ring. On the test Mac about 40,000 frames (55 MB) reached `llw0` in the first minute, none failed or were rejected. **Still not clean:** the video loses packets (the media stack reports 8 of 25 missing with no error correction), and the driver's sequence-number gap counters put the radio-level loss at about 7.5% in bursts. Cause not yet known; see [DEBUGGING.md Case 3](docs/DEBUGGING.md#case-3-continuity-camera-gets-part-of-the-way).
- **New: `llw0`, the low latency companion interface (Sequoia, `-itlawdlllw`).** A second Skywalk interface on the Wi-Fi class chain (role 2, id 9, prefix `llw`, `awdl0` as parent) that macOS asks for with request 293. Needed fixes: a power-state override (the family's handler deadlocks with the 293 handler), the MAC plus `"ll"` as the `ifnet` unique id, power state 1, and answering the BSD ioctls Apple's class rejects. Its virtual table (655 slots) is audited against Apple's by `tools/abi/audit_llw_vtable.py`; `ForbiddenItlwm/AirportLLWHandlers.inc` is generated from it. New flags `itlawdlllwrx` and `itlawdlllwmtu`. See [BOOT-FLAGS.md](docs/BOOT-FLAGS.md).
- **New flag `-itlawdlcoexcam` (experimental): Wi-Fi station without power save.** The camera stream loses about 8.7% of the iPhone's frames at the radio (0 bad CRCs reported, almost all on TID 7), in bursts about every 100 ms and every third one longer, with the Mac associated on channel 161 and AWDL on 149. That timing matches the access point's beacon and DTIM schedule, which the firmware must hear on 161. The flag keeps the station awake so it doesn't need those visits. Whether it removes the loss is not yet tested; moving the access point to channel 149 is the other test.
- **Diagnostics for the receive path.** `ITLAWDLCoexRxRejectReasons` (why a heard data frame was not handed on, from `classifyDataFrame` in `include/AWDLDataFrame.hpp`, with `tools/awdl_rx_rejects.py` to read it), `ITLAWDLCoexRxOuterLengthSamples` (raw bytes of the first rejected frames), 802.11 sequence-gap counters for the iPhone's unicast data (`ITLAWDLCoexSeq*`, including the last 48 gap events with firmware timestamps), and counters for what the firmware reports before any check and where the driver drops: `ITLAWDLRxMpduTotal`, `BadCrc`, `BadOverrun`, `BadCrcRuns`, `DupDropped`, `ReorderHeld`. The last group has not yet been read on hardware. `ItlwmLLW*` keys count `llw0`'s receive, transmit and destinations.
- **Tools:** `tools/diag/llw_attempt.sh` (one 50 s capture of a camera attempt: packet captures, registry, log, `skywalkctl` tables, a `dtrace` trace), `tools/diag/trace_llw_netif.d`, and `tools/abi/kc_carve.py`, `kc_vtable.py`, `gen_llw_handlers.py`, `audit_llw_vtable.py` (reading Apple's class tables out of a kernel collection). `dtrace`'s `fbt` could not see this driver's own functions on the test Mac; see [DEBUGGING.md](docs/DEBUGGING.md#whos-refuses-a-packet-root-dtrace).
- **Tests:** `tests/awdl_data_reject.cpp` (the classifier agrees with `parseDataFrame` on 200,000 mutated frames, accepts plain RFC 1042, and round-trips the plain transmit build; run clean under ASan/UBSan).
- **Found, outside this driver:** on a Mac that reports an old Intel CPU family (the usual AMD "Force Penryn" patch), Continuity Camera is refused before any traffic; Skylake's family (`0x37fc219f`) passes. This repo does not change it.
- **Credits:** added [DrogaBox](https://github.com/DrogaBox) and RTL8814Native. Their notes on the AWDL peer manager's driver interface (the peer cache record, its completion event and when to post it, the cache size) are what the Continuity Camera peer cache handling in 0.5.4-beta.3 follows. No code was copied.
- **Tools:** the camera section of `tools/diag/continuity_check.sh` now follows the stages Continuity Camera passes through: whether the camera agent lists the iPhone, the driver's peer-cache and `-itlawdlumiack` counters, whether macOS accepts this Mac's CPU family for the camera's video format (it asks `canDoHEVC`, read-only), and counts of each failure line in the log. It prints counts only, no names.
- **Tests:** the peer cache completion record (event 51), the UMI status record (message 69) and the bounded list of peers owed a status moved into `ForbiddenItlwm/AWDLPeerCache.hpp`, with a host test (`tests/awdl_peer_cache.cpp`) in `tools/test_awdl.py`. The driver's behaviour is unchanged.
- **Checked:** the Tahoe and Sonoma kexts compile with the Continuity changes and pass their virtual table audits (568 and 547 slots); they have not been run on those macOS versions.

## 0.5.4-beta.3

- **Continuity Camera and Sidecar: the driver now answers the requests macOS makes before it registers real-time traffic.** `setPEER_CACHE_CONTROL` used to return "unsupported", so macOS waited 3 s for an event that never came and failed the registration. The driver now accepts the request and, after its handler has returned, posts event 51 with the same 464-byte record (`+4` = 1 added, 3 deleted, peer address at `+8`). Posting from inside the handler is too early, because the caller has not gone to sleep yet and the wakeup is lost. It also answers `getPEER_CACHE_MAXIMUM_SIZE` (8) and accepts `setLLW_PARAMS`. Counters: `ItlwmAWDLPeerCacheRequests/Completed/LastPeer/LastOperation`, `ItlwmAWDLLlwParamRequests`.
- **New flag `-itlawdlumiack` (off by default): reports the "peer acknowledged our UMI" status.** The next step of the registration sends a unicast action frame (a "UMI") and waits 3 s for its transmit status, message 69 (peer address, then a status byte at `+6`, 0 = acknowledged). macOS sends that frame from a timer that only runs inside an AWDL availability window, and this driver reports no windows (the kernel logs `monitorAWEvents WARNING: Did not get AW start event` every second), so the status never came. With the flag the driver posts it itself. Every wait on `EnsembleUMIStatusDone` then ends at once and the kernel logs "Peer acked Ensemble start UMI request". Counter: `ItlwmAWDLUmiAckPosted`.
- **Found, outside this driver: on an AMD machine the iPhone camera is refused because the CPU family is Penryn.** After the two items above, the stream failed with `VCVideoRuleCollectionsRemoteCameraMac initSupportedPayloads: No supportedPayloads for this hardware`. The cause is `-[VCHardwareSettingsMac canDoHEVC]`, which returns false for a fixed list of older Intel CPU families (Penryn, Nehalem, Westmere, Sandy Bridge, Ivy Bridge, Haswell, Broadwell and a few older ones) and true for Skylake and newer. The AMD Vanilla kernel patch "Force CPUFAMILY_INTEL_PENRYN" makes `hw.cpufamily` 0x78ea4fbc. Changing that patch's immediate to 0x37fc219f (Skylake) made `canDoHEVC` return true on the test Mac. The family is read system-wide, so this is a change to your own OpenCore setup, not something the driver does; see [DEBUGGING.md](docs/DEBUGGING.md#case-3-continuity-camera-gets-part-of-the-way).
- **Still failing: no camera video.** After the stream negotiates, the media stack opens a UDP connection to the iPhone at a per-attempt `fdXX:XXXX:XXXX::NN` address on `awdl0` with the flags "LowLatency Handoff". It times out (`VCTransportSessionNW startNWConnection: nw_connection ready timeout`), because `awdl0` has only a link-local address and no route for that address. macOS may expect an `llw0` interface for this, which the driver does not create. A capture shows nothing is sent, and adding an `fd00::/8` route on `awdl0` for one attempt makes the path satisfied but the connect then fails with `Address already in use` (the session's local UDP port collides with its listener). Not solved.
- **Tools:** `tools/diag/trace_peer_cache.d`, `trace_umi.d` and `trace_umi_chain.d` (what macOS asks of the driver and what it waits for, with stacks), `tools/diag/continuity_check.sh` (read-only per-feature Continuity check), and `tools/oc/ocvalidate.sh` with the matching OpenCore 1.0.8 `ocvalidate` for checking the EFI after every change.
- **Docs:** [DEBUGGING.md](docs/DEBUGGING.md) has a new Continuity Camera case, and `-itlawdlumiack` is in the boot flags.

- **Fix: a Mac → iPhone send could stall for about two minutes after the iPhone had been idle.** The driver kept promiscuous receive off only while a receive Block Ack session was open. That session is torn down after 60 s idle, but the iPhone's firmware station lives up to ten minutes, so a send started in the gap got no replies (the firmware doesn't acknowledge a station's frames with promiscuous receive on). It now stays off for as long as the station exists (`awdlCoexBaHandle`). Measured on an AX200 with macOS Sequoia 15.8.2: the filter stayed off for a six-minute test, setup took 0.1 to 0.9 s, and a 2.8 GB send ran at 34 MB/s. Multicast mDNS answers from the iPhone are received less while it's off, which didn't affect the connections tested.
- **Found, not a driver bug: big AirDrop sends die after about 2 s with `unexpected-40` when a wired interface is at MTU 1500.** AirDrop's QUIC sizes packets from the wired path, and macOS refuses packets over `awdl0`'s 1484 with `EMSGSIZE`. Lowering the wired interface to 1484 fixes it. [TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md#big-airdrop-sends-die-after-a-couple-of-seconds-unexpected-40) has the workaround and how to confirm it.
- **Tools:** `check_compat.sh` has a new section 7 that warns when an active wired interface has a larger MTU than `awdl0`. New `tools/diag/` with a per-flow capture analyzer, a counter logger, an MTU ping ladder and two `dtrace` scripts that find who refuses a packet.
- **Docs:** new [DEBUGGING.md](docs/DEBUGGING.md) (what each registry counter means, how to capture and trace, two worked cases, harmless log noise), two new troubleshooting sections, and `-itlawdlpmdebug` in the boot flags.
- **Tested** on an Intel AX200 (AMD Ryzen 9 5950X desktop), macOS Sequoia 15.8.2 (24H232), 0.5.4-beta.2 with the filter fix: AirDrop both ways, a 2,882,165,196-byte Mac → iPhone send over AWDL at 34 MB/s with 99.6% of aggregated frames acknowledged and no failures counted.
## 0.6.0-beta.1

The first beta of 0.6.0. Everything since 0.5.4-beta.2, including what 0.6.0-alpha.1 tested:

**AirDrop**
- **Channel 44 ([#17](https://github.com/retropineaple/ForbiddenItlwm/issues/17), [PR #21](https://github.com/retropineaple/ForbiddenItlwm/pull/21), [#35](https://github.com/retropineaple/ForbiddenItlwm/issues/35), thanks to zheznanohana).** Apple devices use channel 149 or 44 for AirDrop, each by its own country rules: in Japan, Germany and Russia, for example, iPhones use 44, even where 149 is allowed. The listener used to stay on 149 or fall back to 6. Now, once the driver has heard the iPhone, it follows it: to 44 (at 80 MHz over 36–48 where the firmware allows it, else 20 MHz) if the iPhone uses 44, otherwise 149, then 6. `ITLAWDLCoexPeer5GHz` shows the channel the iPhone uses. Confirmed in Japan at 26 MB/s Mac → iPhone.
- **Faster Mac → iPhone on the same channel ([#22](https://github.com/retropineaple/ForbiddenItlwm/issues/22), [#24](https://github.com/retropineaple/ForbiddenItlwm/issues/24), [PR #47](https://github.com/retropineaple/ForbiddenItlwm/pull/47), thanks to WarnerATCN).** When the Mac's Wi-Fi was on the listener's channel, the iPhone never accepted block ack, so Mac → iPhone went out one frame at a time. A short receive window while asking for block ack fixes it, and is on by default. `-itlawdlnosamechprobe` turns it off.
- **Mac → iPhone sends no longer stall after the iPhone was idle ([PR #57](https://github.com/retropineaple/ForbiddenItlwm/pull/57), thanks to wh0ami7).** The listener's receive filter now follows the iPhone's firmware station.
- **AirDrop's listener survives Wi-Fi reconnects ([PR #12](https://github.com/retropineaple/ForbiddenItlwm/pull/12), thanks to mingww64).** It starts only once the Wi-Fi connection is fully up, removing it waits for a setup still in progress, and a failure to remove it switches AirDrop off until the next firmware restart instead of restarting the firmware.
- **Passive channels next to your Wi-Fi.** Where the firmware marks a channel passive but usable beside a connected network (as in Japan for 36–48), the listener may use it while the Mac's Wi-Fi is connected in the same channel group, following Linux's rule for Wi-Fi Direct interfaces. `-itlawdlnoirconcurrent` turns it off.
- **No 80 MHz overlap with your router ([#26](https://github.com/retropineaple/ForbiddenItlwm/issues/26)).** If the Mac's Wi-Fi uses the listener's 80 MHz block with another main channel (a router on 157 at 80 MHz, for example), the listener uses its channel at 20 MHz; inside a 160 MHz router channel it moves elsewhere.

**Wi-Fi**
- **Wi-Fi reconnects after macOS drops it** (#20, #63). When macOS disconnected Wi-Fi itself (switching or logging out of an account, for example) during one of the driver's background scans, the driver then refused every scan macOS asked for, so Wi-Fi never came back until it was turned off and on. Fixed, and on Tahoe and Sequoia the driver now also tells the router it's leaving, so the next join works on the first try. On the project's hackintosh Wi-Fi rejoins in about 10 s after an account switch.
- **Link quality and signal ([PR #1](https://github.com/retropineaple/ForbiddenItlwm/pull/1), thanks to mingww64):** macOS's link quality goes back to "off" when the driver stops; on Tahoe the measured noise and signal-to-noise are reported where the card's firmware provides them.

**Security**
- A review of 0.6.0-alpha.1 found and fixed problems in code that handles frames from nearby devices, requests from macOS, firmware messages and Bluetooth events. Most are in the Sonoma kext, whose Wi-Fi code takes paths the Tahoe and Sequoia kexts don't use: a 32-character network name returned bytes from kernel memory, scan results used memory that could already be freed, and shutdown freed memory while the hardware could still use it. On all kexts: more length checks on frames and firmware messages, AirDrop's announcement from macOS copied once and checked, a refused Wi-Fi join no longer leaves the Mac set up for an open network of that name, and failed starts clean up after themselves. The driver's log no longer holds network names, Wi-Fi handshakes or full Wi-Fi addresses. How to report security problems: [SECURITY.md](SECURITY.md).

**BTLEAdvFixup 0.9.2**
- The new-LE-device pairing fix no longer takes over the Bluetooth controller's event pipe when a pairing round doesn't finish, and no longer writes to a buffer it couldn't prepare ([PR #61](https://github.com/retropineaple/ForbiddenItlwm/pull/61), thanks to takoyakiwhite). With 0.9.1 that could leave USB devices unresponsive until a cold boot, or panic.
- Pairing rounds are tracked per connection and given up after 2 s, so two devices pairing at once don't mix up their events.
- It no longer edits the Bluetooth stack's own request structure, and a removed advertising set no longer leaves its address to the next one.

**Diagnostics and tools**
- `-itllog` keeps the driver's own log, readable after a failed wake (it can still hold Wi-Fi addresses; see BOOT-FLAGS). Scan counters for missing networks (`ItlwmScanStats`, #20, #24, #45), on every kext including Sonoma, and the channel lists macOS gets.
- `check_compat.sh` checks channels 36–48 as well as 149–161, counts a listener on 44 at 80 MHz as the fast mode, shows which channel your iPhone uses, and checks whether pf has turned off macOS's user-space network path, which can slow AirDrop's QUIC transfers; on Tahoe OpenCore's PowerTimeoutKernelPanic quirk causes it ([PR #59](https://github.com/retropineaple/ForbiddenItlwm/pull/59), thanks to kevineduardo).
- The hardware report scripts list channels 36–48 and handle unusual user and computer names; `airdrop_measure.sh` works under any locale (#21).

**Removed:** 0.5.3's test flags `-itlawdlbaaskshared` and `-itlawdlhideinfra`. Neither helped; they're ignored now.

**Docs:** keep `-itlawdlcoexmulti` where channel 149 isn't available (the listener now follows the iPhone to 44); known limitations: AirDrop needs the Mac to be on a Wi-Fi network, and the WPA2/WPA3 transition behaviour; `bluetoothd` crashing after hours (#62); the diagnostic flags.

**Tested on the project's hackintosh** (Tahoe 26.7.1, AX211, listener on 149): the release build runs, AirDrop at 16–23 MB/s both ways across this release's test builds, Wi-Fi rejoins in 8–13 s after an account switch, Bluetooth audio works. Channel 44 was confirmed by a tester in Japan, and 0.6.0-alpha.1 by testers on Sequoia. The Sequoia and Sonoma builds are built and checked offline; on Sonoma, AirDrop doesn't start yet ([#55](https://github.com/retropineaple/ForbiddenItlwm/issues/55)).

## 0.6.0-alpha.1 (test build)

A test build of 0.6.0's main changes, released to collect results. **Alpha** means it's for testers: it was tested on the project's hackintosh only where that hackintosh can test it (channel 149, Tahoe).

- **Channel 44 ([#17](https://github.com/retropineaple/ForbiddenItlwm/issues/17), [PR #21](https://github.com/retropineaple/ForbiddenItlwm/pull/21), [#35](https://github.com/retropineaple/ForbiddenItlwm/issues/35), thanks to zheznanohana).** Apple devices use channel 149 or 44 for AirDrop, and each picks one by its own country rules: in Japan, Germany and Russia, for example, iPhones use 44, even where 149 is allowed. The listener stayed on 149 or fell back to 6, so the iPhone rarely met it. Now, once the driver has heard the iPhone, the listener follows it: to 44 (at 80 MHz over 36–48 where the firmware allows it, else 20 MHz) if the iPhone uses 44, otherwise 149 as before, then 6. The iPhone's own Wi-Fi channel isn't mistaken for its AirDrop channel. `ITLAWDLCoexPeer5GHz` shows the channel the iPhone uses.
- **Faster Mac → iPhone on the same channel ([#22](https://github.com/retropineaple/ForbiddenItlwm/issues/22), [#24](https://github.com/retropineaple/ForbiddenItlwm/issues/24), [PR #47](https://github.com/retropineaple/ForbiddenItlwm/pull/47)).** When the Mac's Wi-Fi was on the listener's channel, the iPhone never accepted block ack, so Mac → iPhone went out one frame at a time. The fix (a short receive window while asking for block ack), tested by three testers on 149 and 44, is now on by default. `-itlawdlnosamechprobe` turns it off.
- **Mac → iPhone sends no longer stall after the iPhone was idle ([PR #57](https://github.com/retropineaple/ForbiddenItlwm/pull/57), thanks to wh0ami7).** After a minute without data the iPhone ends its receive session, but its station stays for 10 minutes; in between, the listener's receive filter opened up and sends could hang. The filter now follows the station.
- **Passive channels next to your Wi-Fi.** Where the firmware marks a channel passive but usable beside a connected network (as in Japan for 36–48), the listener may use it while the Mac's own Wi-Fi is connected on a channel in the same group, following Linux's rule for Wi-Fi Direct interfaces. `-itlawdlnoirconcurrent` turns it off.
- **No 80 MHz overlap with your router ([#26](https://github.com/retropineaple/ForbiddenItlwm/issues/26)).** If the Mac's Wi-Fi uses the listener's 80 MHz block with another main channel (for example a router on 157 at 80 MHz), the listener now uses its channel at 20 MHz; inside a 160 MHz router channel it moves elsewhere. Beacon hints a country change doesn't affect are kept.
- **Diagnostics:** scan counters for missing networks (`ItlwmScanStats`, #20, #24, #45), the channel lists macOS gets, and `-itllog`, which keeps the driver's log readable after a failed wake.
- **Tools:** `check_compat.sh` checks channels 36–48 as well as 149–161, counts a listener on 44 at 80 MHz as the fast mode, shows which channel your iPhone uses, and no longer says AirDrop must stay on channel 6 in countries without 149. The hardware report scripts list channels 36–48 too.
- **Removed:** 0.5.3's test flags `-itlawdlbaaskshared` and `-itlawdlhideinfra`. Neither helped; they're ignored now.
- **Tested on the project's hackintosh** (Tahoe 26.7.1, AX211, listener on 149): Wi-Fi works, AirDrop at 15–25 MB/s iPhone → Mac and 8–20 MB/s Mac → iPhone, no change on 149 from the new channel logic. Channel 44 needs testers in Japan, Germany or Russia. The Sequoia and Sonoma builds are built and checked offline.
- BTLEAdvFixup is unchanged (0.9.1).

## 0.5.3-test1 (test build)

Two test flags for slow Mac → iPhone transfers (#22, #24). When the Mac's own Wi-Fi is on the same channel as the AirDrop listener (usually 149), the iPhone never accepts block ack, so frames go out one at a time. On any other channel it accepts within a second. These flags test two explanations; neither is on by default:

- **`-itlawdlbaaskshared`:** in that case, send the block-ack request without waiting for the iPhone's window. The driver's window check held back thousands of requests there. `ITLAWDLCoexBaAsksShared` counts the requests sent this way.
- **`-itlawdlhideinfra`:** leave the Mac's Wi-Fi network and channel out of AirDrop's sync frames (the infrastructure fields of the Data Path State TLV, as described by seemoo-lab/owl). The iPhone then sees a Mac that isn't on Wi-Fi. `ItlwmAWDLSyncInfraStripped` counts the frames changed.

Workaround until one of them becomes the default: put your router (or the Mac's network) on a channel other than the listener's, for example 36–48 or 157.

## 0.4.0-beta1

Everything from the 0.3.1-test1 test build (below), plus:

- **Security fixes.** A review of the driver found these, and they're fixed:
  - **Wi-Fi password handshake (WPA/WPA2):** a length check in the handshake code could be fooled by a malformed message, letting a malicious access point, or anyone who knows the network's password, corrupt kernel memory. This code comes from itlwm and OpenBSD.
  - **An old join function** copied network name and key lengths without checking them. Normal joins don't use it, but it now refuses anything that doesn't fit.
  - **The AirDrop announcement copy (`-itlawdlmitx`)** now only runs on macOS builds whose data layout was verified, so it stays off with `-itlawdlanybuild` and on unverified Sequoia versions (`ItlwmAWDLMiState` shows which). It only keeps data that looks like a real announcement. With `-itlawdlsamples`, a kernel address is no longer published in the I/O Registry.
  - **Memory and shutdown:** two memory leaks on rejected Wi-Fi frames, packets not handed back when the AirDrop interface stops, power callbacks that could run after the driver stopped, a use-after-free after a failed start, and a once-a-second health check (the watchdog) that ran without the driver's lock.
  - **One card only:** a second supported Intel Wi-Fi card is now left alone instead of corrupting the first one's state.
- **WPA2/WPA3 networks rejoin after a reboot.** Networks offering WPA2, PSK-SHA256 and WPA3 together were shown to macOS as WPA3, which the driver can't complete, so auto-join failed and macOS gave up on the whole network. They're now shown as WPA2, as with the original AirportItlwm, and the driver no longer picks PSK-SHA256 without protected management frames. Thanks to lucassaureliano (issue #9), alikaylan (issue #5) and mingww64, whose PR #1 carries the same fix.
- **BTLEAdvFixup 0.8.2:** its state is locked between threads; commands it adds time out after a second and are retried if they fail; it only acts on Intel Bluetooth controllers; and a removed advertising set no longer keeps its old random address. Its patterns also cover 26.7.2, whose `bluetoothd` matches 26.7.3's (thanks to ZEQ-Avidia, issue #8).
- **`check_compat.sh`:** no longer counts one Bluetooth pattern twice, which made it warn on 26.7.3 (issues #5, #8), and the listener check uses a more portable `grep`.
- **Removing BTLEAdvFixup before a macOS update:** an incremental update can fail while `bluetoothd` is patched (issue #8). Boot once without `-btleadv` before updating.
- **Tested** on the project's hackintosh (AX211, 26.7.1): WPA2 and open networks, AirDrop both ways, Bluetooth devices, Wi-Fi off and on, and restarts. Sleep wasn't tested.
